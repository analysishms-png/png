==========================
SECTION 1: DATA MODEL (CORE TABLES)
==========================

Front Office ka poora system 6 core tables pe khada hai. Har screen/report inhi
me se ek ya zyada tables ko padhti (SELECT) ya likhti (INSERT/UPDATE) hai:

1. guestfolio -> Master bill ledger (har check-in ka ek Docid; folio_no unique)
 Columns: Docid, folio_no, mFoliono (merge ke liye), guestprof (FK), vdate
 (check-in date), name, city, arrfrom, destination, purvisit, company,
 travelagent, busssource, bookingdocid, complimentry, rodisc, remark
 LOGIC: Saare charges/payments 'paycharge' me iske Docid (folionodocid) se
 judte hain. mFoliono tab use hota hai jab do folio merge hote hain.

2. roomocc -> Room occupancy rows (check-in ki actual room details)
 Columns: Docid (FK=guestfolio), foliono, sno/sno1 (repeated stays), roomno,
 newroomno (room change!), chkindate, chkintime, chkoutdate, chkouttime,
 depdate, deptime (expected departure), adult, children, roomrate, plancode,
 planamt, ratecode, roomcat, type ('O' = occupied, day-use bhi), chngdate
 (room change date), reasonrchange, RRTaxInc
 LOGIC: Check-out hone pe chkoutdate set hota hai. Isliye:
 - IN-HOUSE guests = chkoutdate IS NULL
 - Checked-out = chkoutdate IS NOT NULL
 - Room change = newroomno NOT NULL aur newroomno <> roomno

3. guestprof -> Guest profile (repeat guest ka ek hi profile reuse hota hai)
 Columns: guestcode, Name, mobile_no, nationality, gender, age, id_proof,
 idproof_no, guest_status, compliementry flag, docid link
 LOGIC: 'Add New Profile' screen isme entry banata hai. Occupancy report
 isse nationality/ID/gender laata hai.

4. paycharge -> SAARE financial transactions (charges + payments)
 Columns: DOCID, SNO, SNO1, FOLIONO, FOLIONODOCID, VDATE, VTYPE (RC=room
 charge, ARRES/ADRES=advance settle, CHK=checkout bill, BANRES etc.),
 VNO, PayCode (revenue code jaise RMCH=Room Rent), PayType (Cash/UPI/
 Card), AmtCr (credit=charge), AmtDr (debit=payment), TipAmt, comp_code,
 RESTCODE (FOM=Front Office desk), refdocid (settlement link), DbtChkIn,
 U_Name, Comments
 LOGIC: Ye table FO, POS, Banquet, Laundry sab ka common ledger hai.
 RESTCODE batata hai kaunsa desk entry ki. Net = AmtCr - AmtDr.

5. room_mast + room_cat -> Rooms aur categories
 room_mast: rcode (room no), room_cat, type='RO' (room), InclCount ('Y'
 matlab occupancy/inventory count me aayega), building, floor, features
 room_cat: cat_code, Name, NoOfRoom, rate
 LOGIC: Room Inventory report InclCount='Y' wale hi rooms ginata hai.

6. Mastertables: plan_mast (plans CP/MAP/AP + tarrif), revmast (revenue heads,
 field_type 'C'=charge/'P'=payment, Desk_code=FOM), subgroup (companies/
 travel agents/OTA - comp_type se), busssource (market segment), gueststats
 (guest status), rate_list (rack rates), fom_billdetail (printed bills,
 status='Cancel' track hota hai)

SECTION 2: MASTER SCREENS - LOGIC (10 screens)
==========================

[2.1] FOM Parameter (/fomparameter, code 121211)
PURPOSE: Poore FO module ki global settings.
LOGIC: Ye values har check-in/checkout/bill pe apply hoti hain -
 - Checkout time, tax inclusive flags (RRTaxInc), GRC print format,
 - Auto folio number series, night audit lock rules
 - Property-level policies jo Controllers constructor me padhte hain
DB: fomparameter / companyreg tables.
TRAINING POINT: Idhar galat setting = poori property ke bills pe effect.

[2.2] Business Source (/businesssource, 121212)
PURPOSE: Market segments (Walk-In, OTA, Corporate, Agent, Web direct...)
DB: busssource (bcode, name, propertyid)
LOGIC: Reservation/WalkIn form me isme se select hota hai aur guestfolio.
busssource me store hota hai. Revenue Source Report isi ko GROUP BY karke
har segment ka revenue nikalta hai.
LOGIC CHAIN: busssource -> guestfolio.busssource -> paycharge(revenue) -> report

[2.3] Guest Status (/gueststatus, 121213)
PURPOSE: Guest categories (VIP, Regular, Corporate guest...)
DB: gueststats (gcode, name)
LOGIC: guestprof.guest_status FK. Occupancy report me GuestStatus column
isi se aata hai (join: guestprof.guest_status = gueststats.gcode).

[2.4] Charge Master (/chargemaster, 121214)
PURPOSE: Extra charges heads (Laundry, Mini Bar, Extra Bed, Damage...)
DB: revmast (rev_code pattern: <CODE><propertyid> e.g. LNDY103)
LOGIC: revmast.field_type='C' (charge) aur Desk_code batata hai kaunsa
module use karega (FOM/POS...). Front Office ke revenue columns
Sale Summary/CheckOut Register me isi ke seq_no order me aate hain.
SPECIAL CODES jo reports me EXCLUDE hote hain: ROFF=Round Off, DISC=Discount,
CGSS/SGSS=GST heads, TOUT=Transfer Out, RMCH=Room Rent.

[2.5] Plan Master (/planmaster, 121215)
PURPOSE: Tariff plans - EP (room only), CP (breakfast), MAP (breakfast+dinner),
AP (all meals)
DB: plan_mast (pcode, name, tarrif)
LOGIC: roomocc.plancode FK. Night Audit isse decide karta hai ki room rent ke
saath kaunse meal charges auto-post karne hain (planamt ke hisaab se).
Occupancy Report me 'package' column = plan_mast.name.

[2.6] Room Features (/roomfeatures, 121216)
PURPOSE: Amenity tags (Balcony, Sea View, AC...)
DB: roomfeatures table; room_mast se link
USE: Room availability dikhaate waqt guest ko features dikhane ke liye.

[2.7] Room Category (/roomcategory, 121217)
PURPOSE: Room types (Deluxe, Super Deluxe, Suite...)
DB: room_cat (cat_code, Name, NoOfRoom, rate)
LOGIC: room_mast.room_cat FK. Availability = NoOfRoom - occupied(us type ke).
Rate list category-wise banti hai (rate_list.room_cat).

[2.8] Room Master (/roommaster, 121218)
PURPOSE: Har physical room ki entry (101, 102, 1151...)
DB: room_mast (rcode, room_cat, type='RO', InclCount, building, floor)
LOGIC: Room Status board aur Room Inventory isi se rooms laate hain.
InclCount='Y' = inventory/occupancy % me count hoga. 'N' wale (jaise
lobby-attached store) count se bahar.

[2.9] Booking Source (/bookingsource, 121219)
PURPOSE: Reservation aaye kahan se (Booking.com, MakeMyTrip, Direct call)
DB: bookingsource / booking.bookedby
LOGIC: 'booking' table me har reservation ka bookedby hota hai. Room Inventory
report booking.bookedby + busssource join karke Market Segment dikhata hai.

[2.10] Building Master (/buildingmaster, 121220)
PURPOSE: Buildings/blocks (Main Wing, Annexe...)
DB: buildingmast; room_mast.building FK
USE: Room-wise filters, HK assignment, block-wise occupancy.

SECTION 3: OPERATIONS SCREENS - LOGIC (11 screens)
==========================

[3.1] Blank GRC (/openblankgrc, 141111)
PURPOSE: Khali Guest Registration Card print karna (walk-in pehle likhne ke liye)
LOGIC: Sirf print template - data nahi padhta. GRC me wahi fields hain jo
WalkIn Check In me digitally bharte hain (naam, address, ID, dates, rate).

[3.2] Walk-In Check In (/walkincheckin, 141112) - Shift+W
PURPOSE: Bina reservation ke guest ko turant room dena. FO ka SABSE ZYADA use
hone wala flow.
LOGIC (CheckinController):
 STEP 1: Room availability room_mast vs roomocc (chkoutdate IS NULL) se
 STEP 2: Guest profile - existing guestprof search mobile no. se, mila to
 reuse (repeat guest), na mile to naya profile insert
 STEP 3: guestfolio INSERT (vdate=aaj, folio_no naya, busssource etc.)
 STEP 4: roomocc INSERT (Docid FK, roomno, chkindate=NOW, roomrate, plan)
 STEP 5: Advance liya to paycharge INSERT (VTYPE=ADRES, AmtCr, PayType)
 STEP 6: Room status 'O' (occupied) ho jata hai - Room Status board me dikhta hai
TRANSACTION SAFETY: Sab inserts ek DB transaction me - beech me fail hua to
rollback (aadha folio kabhi nahi banta).

[3.3] CheckIn List (/checkinlist, 141113)
PURPOSE: Aaj (ya date range) ke saare check-ins ki list.
LOGIC: guestfolio JOIN roomocc WHERE vdate BETWEEN fromdate AND todate.
Columns: folio, guest, room, pax (adult+children), rate, plan, in/out datetime,
advance (SUM paycharge.amtcr WHERE modeset!='S').
ADVANCE ka logic: modeset='S' = settled/adjusted entries list me nahi aate.

[3.4] Room Status (/roomstatus, 141114) - Shift+S
PURPOSE: Poora hotel ka live board - kaunsa room khali, bhara, dirty, OOO.
LOGIC: room_mast (saare rooms) LEFT JOIN roomocc (chkoutdate IS NULL).
Jo room roomocc me nahi mila = VACANT. HK tables se cleanliness status.
Isi board se room click karke check-in/assign karte hain.

[3.5] Bill Reprint (/billreprint, 141115)
PURPOSE: Purana printed bill dobara nikalna (guest copy kho gayi / audit copy)
LOGIC (Reporting.php billreprintsubmit):
 fom_billdetail table se original bill data (billno, billdate, items, taxes)
 Read-only reprint - naya voucher NAHI banta, accounting me koi effect nahi.
 Search: bill no / folio / guest name / barcode.

[3.6] Bill Re-Settlement (/billresettle, 141116)
PURPOSE: Settle hua bill galat mode se settle kiya tha (Card ki jagah Cash) -
 usko undo karke dubara settle karna.
LOGIC:
 1. Purani settlement ki paycharge entries reverse (AmtDr undo, refdocid link)
 2. Bill status wapas 'open'
 3. Naya settlement entry banti hai (naya VNO)
 4. fom_billdetail me naya bill record - purana superseded
AUDIT: Purani entry delete NAHI hoti - reverse entry ke through trail banta
hai (accounting best practice).

[3.7] Misc Payment/Rect. (/expsheet, 141117)
PURPOSE: Folio ke bahar ke cash transactions - petty cash, corrections,
non-guest payments.
LOGIC: paycharge me direct entry bina folio link ke (ya special folio).
VTYPE rectification/expense codes. Cashier Report me 'PAYMENT RECD' ke saath
ya alag section me dikhta hai.

[3.8] Merge Folio (/mergefolio, 141118)
PURPOSE: Ek hi guest/company ke multiple folios ko ek bill me jodna
LOGIC:
 1. Target folio chuno, dusre folios ka Docid target ke mFoliono me daalo
 2. Saare paycharge rows ka FOLIONODOCID target Docid pe update
 3. roomocc rows bhi move (agar same guest ke rooms hain)
 4. Bill ab combined banega - ek hi settlement me
REVERSE Merge Folio (141119): Ulta operation - mFoliono reset, paycharge
wapas original folio Docids pe (merge ke andar ke order me).

[3.9] In House Room Status (/inhoseroomstatus, 141120) - Shift+I
PURPOSE: Abhi hotel me ruke guests ka detailed view - folio balance ke saath.
LOGIC: roomocc (chkoutdate IS NULL) JOIN guestfolio JOIN guestprof +
SUM(paycharge.AmtCr - AmtDr) per folio = LIVE BALANCE.
Front desk isse checkout se pehle balance confirm karti hai.

[3.10] Add New Profile (/addnewprofile, 141121)
PURPOSE: Bina check-in ke guest profile banana (future booking ke liye)
LOGIC: guestprof INSERT. Guest code generate hota hai jo baad me WalkIn/
Reservation me reuse hota hai (mobile/naam se search karke).

[3.11] Ammend Stay (checkinlist ke andar se)
PURPOSE: Guest ke dates/room/rate change karna bina naya folio banaye
LOGIC: roomocc UPDATE - depdate/bade dates, roomno, roomrate. Room change ho
to: roomno purana rehta, newroomno set, chngdate set, sno+1 nayi row -
isliye Room Change History possible hai.

[4.3] Cashier Report (/cashierreport, 141213) - DATED SCREENSHOT 03
SOURCE: Reporting.php::fetchcashierreportdata + fetchcashierreportdata2
QUERY LOGIC (payment side):

 WHERE PC.RESTCODE='FOM' AND VDate BETWEEN dates
 AND ( (VTYPE IN (ARRES,ADRES) AND DbtChkIn<>'Yes')
 OR (VTYPE NOT IN (ARRES,ADRES) AND (refdocid IS NULL OR refdocid='')) )
 AND VTYPE <> 'CHK'

ISKA MATLAB (plain words):
 - Advance settlements (ARRES/ADRES) tabhi aate hain jab wo check-in pe
 applied NA hue (DbtChkIn)
 - refdocid linked entries = jo pehle hi kisi settlement me gayi - skip
 (double-count na ho)
 - CHK (checkout settlement voucher) alag query (data2) se aata hai
MODE-WISE TOTALS: Cash/UPI/Card/Company paytype ke SUM - cashier ka din.
USE: Shift-handover pe cash drawer vs system match karna (cash reconciliation).

SECTION 5: KEY CODE PATTERNS (DEVELOPER/ADVANCED TRAINER KE LIYE)
==========================

1. PERMISSION CHECK (har screen pe pehla block):
 $permission = revokeopen(<code>); // e.g. 141211
 if (is_null($permission) | | $permission->view == 0) -> "no permission"
 CODE FORMAT: MMGGSS = Module(2) Group(2) Screen(2)
 14=Front Office | 11=Operations, 12=Reports, 13=MIS, 15=Tax
 Menu system isi code se khulta hai (fetchsubmenu/fetchlastmenu opt1/opt2/opt3)

2. MULTI-TENANCY: har query me propertyid filter (103) - multi-hotel cloud
 architecture ka core. Kabhi bhoolna nahi ki data isolation isse hota hai.

3. FINANCIAL DUALITY: paycharge me AmtCr (charges/guest ko debit) vs
 AmtDr (payments/guest ne diya). Folio balance = SUM(AmtCr) - SUM(AmtDr).
 Checkout allowed jab balance settle = 0.

4. DATE LOGIC GOTCHA: "From-To date" ka matlab report pe depend karta hai:
 - checkinreg: guestfolio.vdate (check-in date range)
 - occupancy: overlap logic (chkindate<=to AND chkoutdate>=from OR null)
 - expectedcheckout: depdate range BUT chkoutdate IS NULL
 - cancel bill: billdate range
 Training me ye difference samjhana ZARURI hai.

5. SETTLEMENT CHAIN: ADRES/ARRES advance -> DbtChkIn flag (folio pe applied?)
 -> CHK checkout voucher -> refdocid links settlement to bill -> cancel =
 status change. Cashier Report isi chain ko double-count se bachata hai.

6. MERGE TRAIL: mFoliono (guestfolio) + FOLIONODOCID re-point (paycharge) +
 reverse-merge helper - kabhi physical delete nahi.
