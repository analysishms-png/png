POS MODULE FIX PLAN
===================

VB6 logic extracted from legacy POS patterns:
- KOT entry and sales flows are based on outlet/restaurant department codes and daily revenue posting.
- POS posting is grouped by RestCode + RevCode and then posted as PayCharge with Vtype = PPOS / revenue logic.
- Night audit checks Enviro flags before posting room charges and POS revenue and logs the result.
- Sales reports are chosen by index and follow case-based report dispatch.

Scope:
- POS masters
- KOT / POS entry
- POS status / display
- Sales register / item-wise sales flow
- Night audit POS posting

Primary Files:
- HMS_py/core/pos.py
- HMS_py/core/pos_entry.py
- HMS_py/core/pos_masters.py
- HMS_py/core/nightaudit.py
- HMS_py/ui/pos_masters_ui.py
- HMS_py/ui/kot_entry.py
- HMS_py/ui/pos_na.py

Crystal / print pages and names:
- RsKOTEntry / RsPOSDisplay / RsMenuItemEntry / RsTouchScreen / POSBillPrint / RSSaleBill
- rPOSRepView / POS sales report preview / print forms / item-wise sales report family
- Temp printing setup: KOT/POS bill print to local report/temp path; printer config from Analysis.ini and Enviro settings
- Night audit report pages: NightAuditRR, Daily Report, Daily Report-II, RevAnalysis, FOCC Report, Food Cost, FBCostStatement

VB6 behavior to preserve:
1. Revenue should aggregate by RevCode / RestCode and respect live outlet mapping.
2. Night audit should verify KOT and unsettled bill conditions before posting.
3. POS reports and posting should not assume all revenue codes are valid.
4. Duplicate posting must be prevented when the same date/outlet/revenue combo is already posted.

Known Missing / Risky Logic:
1. POS entry must validate outlet / department codes and menu item linkage.
2. KOT posting should check live stock or sales logic before write.
3. Night audit POS post should avoid duplicate posting and stale revenue assumptions.
4. Item-wise sales and outlet grouping require exact VB6 case mapping.
5. POS posting must not blindly assume all revenue is positive or all outlets are active.

Required Fixes:
1. Confirm all POS-related tables exist in the live DB and map to actual columns.
2. Add validation for RevCode, RestCode, SunCode, and outlet grouping.
3. Prevent duplicate posting in Night Audit using safe checks before insert.
4. Use DB-driven grouping for outlet/restaurant revenue, not hardcoded assumptions.
5. Add safe fallback if an item or department is missing from the DB.

Implementation Steps:
1. Re-check live POS tables and their real names.
2. Build a safe posting flow for KOT and revenue aggregation.
3. Add regression tests for:
   - duplicate PPOS skip
   - invalid outlet rejection
   - night audit flag handling
4. Verify no duplicate revenue row is created on repeated run.

Expected Result:
- POS workflows remain close to VB6 behavior while avoiding unsafe writes.
- KOT and revenue posting behave consistently across repeated runs.
- Night audit remains idempotent where required.
