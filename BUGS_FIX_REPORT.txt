BUG #1: MENU NESTING LOGIC - FLAG VALUES CONFUSION
---------------------------------------------------
SEVERITY: HIGH - Causes incorrect menubar rendering
LOCATION: core/menu.py _build_dropdown() function, shell.py _form_registry()
FIX: Implement proper flag-based nesting

Evidence from VB6 decompilation:
- flag='9': Sidebar root node (Analysis.ini key 9 list)
- flag='1': Submenu header - creates dropdown in menubar
- flag='0': Leaf child item - appears under flag=1 parent with SAME 'code'
- BUG: Previous implementation flattened nesting, treating all flag=0 as top-level

CORRECT LOGIC (implemented in rebuild_menu_dynamic.py):
```python
def _build_menu_from_db(module_name, allowed_srnos):
    rows = db.query(...)  # flag<>9 items ordered by srno
    out = []
    cur = None
    for r in rows:
        it = {"name": name, "code": code, "srno": srno, "children": [], "flag": flag}
        if flag == "1":          # NEW: flag=1 => submenu header
            cur = it
            out.append(cur)
        elif cur is not None and code == cur["code"]:  # NEW: same-code => children
            if leaf_ok(it):
                cur["children"].append(it)
        else:                    # NEW: different code => reset parent
            cur = None
            if leaf_ok(it):
                out.append(it)
    return [it for it in out if it["children"] or leaf_ok(it)]
```

BUG #2: MENU NAME NORMALIZATION - HMS SUFFIX NOT STRIPPED
----------------------------------------------------------
SEVERITY: HIGH - Menu rights check fails for names with "- HMS" suffix
LOCATION: core/menu.py menu_name_allowed(), core/menu_help.py flag_for(), can(), can_open()
FIX: Normalize names by stripping "- HMS_py" and "-HMS" before comparison

Evidence: menu.py:73-84 normalization code:
```python
def _normalize(value: str) -> str:
    v = str(value).strip()
    v = v.replace("- HMS_py", "").strip()
    v = v.replace("- HMS", "".strip())
    v = "".join(ch for ch in v if ch not in "\r\n")
    while "  " in v:
        v = v.replace("  ", " ")
    if "(" in v and v.rstrip().endswith(")"):
        base = v.rsplit("(", 1)[0].strip()
        if base:
            v = base
    return v.strip().lower()
```

LOCATION: core/menu.py user_allowed_srnos(), menu_name_allowed()
FIX: If User1.query() returns empty rows for ANY user => full access

Current code (menu.py:51-58):
```python
def user_allowed_srnos(username: str) -> set | None:
    rows = db.query("SELECT SRNO FROM User1 WHERE USER_NAME = ?", (username,))
    if not rows:
```

BUG #8: MENUHELP PERMISSIONS - WRONG DEFAULT WHEN ROW EXISTS BUT PARAM_STR EMPTY
---------------------------------------------------------------------------
SEVERITY: MEDIUM - Forms show wrong permission status when menuHelp row exists but Param_Str is empty
LOCATION: core/menu_help.py rights(), can()
FIX: Default to "AEDP" only when row exists but Param_Str is empty; if row exists with value, use it

Current code (menu_help.py:99-105):
```python
def rights(username, caption):
    row = by_caption(username).get(_norm_caption(caption))
    if not row:
        return "AEDP"  # No row => full access - CORRECT
    p = row.get("param") or ""
    return p if p else "AEDP"  # Row exists but empty => also AEDP - MAY BE WRONG
```
Fix: Only return "AEDP" default if truly no row; if row exists, use whatever Param_Str value is there.
